# 送金スキームの選択肢

拾得者へのお礼(謝礼)をどう届けるか。現行は「当事者間で直接」だが、将来
「アプリ内で完結」に寄せる場合の選択肢を比較する。

> 大原則: **運営の口座・残高を資金フローに通さない**。個人間の資金を預かって渡すと
> 「為替取引」に当たり、資金移動業の登録なしには行えない(`docs/legal-risks.md` B)。
> どの方式でも、着手前に資金決済に強い弁護士と対象事業者の確認を取ること。

---

## 用語

| 用語 | 意味 |
|---|---|
| 為替取引 | 隔地者間で資金を移動する仕組み。銀行と資金移動業者だけが業として行える |
| 資金移動業 | 為替取引を行うための登録業。2021 年施行の改正で 3 類型に(下記 D) |
| 収納代行 | 代金の受け取りを代行する行為。2020 年改正で「債権者が個人」の類型(割り勘アプリ型)は為替取引に当たると明示 |
| 前払式支払手段 | 商品券・プリペイド・デジタルギフト等。自社だけで使える「自家型」は届出、他社でも使える「第三者型」は**発行登録**が必要 |

---

## 方式の比較

| 方式 | お金の流れ | 運営の立場 | 拾得者の手間 | 実装コスト | 法的な要注意点 |
|---|---|---|---|---|---|
| **現行: 当事者間直接** | 持ち主 → 拾得者(運営を通らない) | 送り先情報の橋渡しと自己申告記録のみ | メール/PayPay の登録だけ | 済(実装済み) | ほぼなし。運営が資金に触れない |
| **A. ギフト API 経由** | 持ち主 →(決済代行)→ ギフト事業者が発行 → 拾得者 | ギフトコード発注の取次。残高プールしない | メール登録だけ | 中 | 「送金の潜脱」と見られない設計。都度発行 |
| **B. 資金移動業者 API** | 持ち主 →(ライセンス保有事業者)→ 拾得者 | API を呼ぶだけ。ただし建て付け次第で当事者扱いの恐れ | 事業者による(口座/アプリ連携) | 中〜高 | 「運営の資金を運営の指示で動かす」形だと運営が為替取引の当事者 |
| **C. Stripe Connect** | 持ち主 →(Stripe)→ 拾得者へ payout | プラットフォーマー。手数料徴収も可 | 受取人オンボーディング(本人確認) | 中 | 少額謝礼には本人確認が重い。国際ブランド規約 |
| **D. 自前で資金移動業登録** | 持ち主 →(運営)→ 拾得者 | 送金の主体そのもの | 少ない | 非常に高 | 登録・保全・KYC・検査対応。小規模には過剰 |

**当面は現行のまま。次の一手は A。規模拡大時に C か D を検討。**

---

## 現行方式(当事者間直接)の詳細

アプリの役割は「誰に・いくら・どこへ送るか」を持ち主に見せることだけ。

| 受け取り方法 | フロー |
|---|---|
| デジタルギフト | 拾得者がメアド登録 → 持ち主が「お礼」ページでメアドを見て、**自分で** Amazon ギフト / giftee Box / QUO カード Pay 等を購入してそのメアドへ送信 → 「送金済みにする」 |
| PayPay 送金 | 拾得者が PayPay 登録済みのメアド/携帯番号を登録 → 持ち主が **自分の** PayPay アプリの「送る」で個人間送金 → 「送金済みにする」 |
| 銀行振込(将来追加する場合) | 拾得者が口座情報を登録 → 持ち主が **自分の** ネットバンキングで振込 → 「送金済みにする」 |

- 「送金済みにする」は持ち主の自己申告。実送金の証跡は取らない
- メリット: 法的にクリーン、実装ゼロ、手数料ゼロ
- デメリット: 送金の確実性・追跡が弱い。持ち主が送らないリスク。拾得者側で受領確認できない

## A. ギフト API 経由(推奨する次の一手)

### 事業者の例

- **giftee for Business** — API でギフト券を発行・送付。多ブランド
- **デジコ(DIGGLE 系)** / **EJOICA セレクトギフト** / **QUO カード Pay(法人向け)** など

これらは **第三者型前払式支払手段の発行登録**(または銀行等)を持つ事業者。運営は
「ギフトの発行を発注する」立場に立つ(物品の購入に近い)。

### フロー

```
持ち主が「お礼」ページで「お礼を送る」
  ↓
決済代行(Stripe 等)で ¥1,000 + 手数料を持ち主から収受
  ↓
その注文で、ギフト事業者 API にコード発行をリクエスト(都度発行)
  ↓
拾得者の登録メールへギフトURL/コードが直送される
  ↓
return_case / reward を paid に更新、両者に通知
```

### 設計上のポイント

- **残高としてプールしない**。持ち主の支払 1 件につきギフト 1 件を都度発行する
  (資金を滞留させると資金移動業/前払式の論点に近づく)
- 集金は決済代行(Stripe / GMO 等)に任せ、運営の銀行口座を経由させない設計を検討
- 発注〜発行が失敗した場合の返金導線
- 手数料の名目(システム利用料)と課税(消費税・インボイス)

### 着手前チェックリスト

- [ ] 弁護士に「このスキームで運営が為替取引の当事者にならないか」を確認
- [ ] ギフト事業者に「プラットフォーム経由の都度発行・第三者への送付」が規約上 OK か確認
- [ ] 決済代行の規約(取扱可能な商材か)を確認
- [ ] 必要なら財務局へ事前相談 / ノーアクションレター

## B. 資金移動業者 API

Kyash・pring・Wise など法人向け送金 API を使う。送金の主体はライセンス保有の
その事業者で、運営は API を呼ぶだけ……という建て付けにできるかがすべて。

- 「運営が集めた資金を、運営の指示で受取人に渡す」形だと、運営自身が為替取引の
  当事者と評価されうる
- 「持ち主が事業者に対して直接送金指図し、運営は UI だけ」に寄せられるか、
  事業者・弁護士とスキームを詰める必要がある
- A よりコスト・不確実性が高い

---

## C. Stripe Connect(Express)

- 拾得者が受取人として Stripe にオンボーディング(本人確認・口座登録は Stripe 側)
- 持ち主が Stripe で支払い → Stripe が拾得者へ payout
- 運営は「プラットフォーム」として手数料を取れる。資金は Stripe のフローに乗る
- デメリット: 少額の謝礼に対して拾得者の本人確認が重く、離脱率が上がる
- `docs/legal-risks.md` の Stage B+ に相当。規模が出てきてから

---

## D. 自前で資金移動業登録(参考)

小規模には過剰だが、選択肢として。2021 年施行の改正で 3 類型:

| 類型 | 1 回の上限 | 規制の重さ |
|---|---|---|
| 第一種 | 上限なし | 最重。資金は滞留させず即時送金。認可制 |
| 第二種 | 100 万円以下 | 従来の資金移動業に相当 |
| 第三種 | 5 万円以下 | 参入規制・資金保全が最も軽い |

KAEKURU の ¥1,000 なら第三種で足りるが、それでも:

- 財務局への登録申請(事前相談 → 審査で数ヶ月)、最低純資産要件
- 利用者資金の保全(供託・保証金・信託を滞留額の 100% 超)
- 犯収法の特定事業者として本人確認(KYC)、疑わしい取引の届出
- 社内規程、兼業リスク管理、定期報告、当局検査対応
- 無登録での為替取引は刑事罰(資金決済法 107 条)

## フェーズ計画

| フェーズ | 送金 | 運営の関与 | 前提 |
|---|---|---|---|
| 今(MVP / デモ) | 当事者間直接。送り先表示 + 自己申告 | ゼロ | 実装済み |
| 次 | A: ギフト API + 決済代行。都度発行 | 発注の取次のみ | 弁護士 + 事業者確認、決済代行契約 |
| 規模拡大時 | C: Stripe Connect、または D: 資金移動業(第三種)登録 | プラットフォーマーとして本格関与 | 体制構築、当局対応 |
